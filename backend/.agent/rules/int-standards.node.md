# INT Node.js Engineering Standards

You are assisting an engineering team at INT on an Express + Mongoose REST
API. Whenever you write, refactor, or suggest Node.js code, you must strictly
adhere to the following rules:

## 1. Code Style and Structure
* Use ES6+ syntax consistently (`const`/`let`, arrow functions, destructuring,
  template literals). Never use `var`.
* Use CommonJS (`require`/`module.exports`) to match this project's existing
  module system unless the team has explicitly migrated to ESM.
* Always use `async/await` for asynchronous operations, including all
  Mongoose queries. Do not use raw Promise chains (`.then().catch()`) or
  callbacks unless interacting with a legacy library that strictly requires
  it.
* Follow the existing layered structure: routes (`src/routes/`) stay thin and
  delegate to controllers/services; controllers orchestrate; Mongoose models
  own schema and data-access logic. Keep functions small and single-purpose.
* Use descriptive variable, function, and route-handler names. Avoid
  single-letter variables except in standard loop counters (`i`, `j`).

## 2. Error Handling
* Wrap all asynchronous route handlers and service calls in `try/catch`, or
  use a shared `asyncHandler` wrapper so promise rejections are never
  unhandled.
* Never swallow errors. Log error details (message, stack, request context)
  using a structured logger such as Winston or Pino — not `console.log`.
  `morgan` stays for HTTP access logging only; it is not an error logger.
* Centralize error responses through a single Express error-handling
  middleware. Return structured JSON in the shape
  `{ "error": { "message": "...", "code": "..." } }` with the correct HTTP
  status code — never leak stack traces or raw Mongoose/MongoDB errors to the
  client.
* Translate Mongoose validation errors (`ValidationError`) and cast errors
  (`CastError`, e.g. malformed ObjectId) into 400-level responses rather than
  letting them surface as 500s.

## 3. Security
* Never hardcode secrets, API keys, or the MongoDB connection string. Always
  read them from environment variables via `process.env` (loaded through
  `dotenv`), and never commit `.env` files.
* Validate and sanitize all incoming request data (`body`, `params`, `query`)
  at the route boundary using a schema validator (e.g. `zod`, `joi`, or
  `express-validator`) before it reaches a controller or model.
* Define explicit Mongoose schemas (types, `required`, `enum`, length limits)
  and never pass raw `req.body` straight into `Model.create()`/`findOneAndUpdate()`
  — allowlist fields to prevent mass-assignment.
* Avoid `eval()` or constructing dynamic code/regex from user input. Set
  security headers with `helmet` and restrict `cors` to known origins rather
  than a wildcard in production.

## 4. Performance
* Prevent event-loop blocking: never run synchronous CPU-heavy work
  (large sync JSON parsing, sync crypto, sync file I/O) on a request path;
  offload it to a worker thread or background job.
* Avoid N+1 query patterns — use Mongoose `.populate()` deliberately and
  batch lookups instead of querying inside a loop.
* Add indexes (`schema.index(...)`) for every field used in a frequent query
  filter or sort, and use `.lean()` for read-only queries that don't need
  Mongoose document methods.
* Reuse a single Mongoose connection (connection pooling) across the app
  instead of reconnecting per request.

## 5. Guardrails
* Never include comments indicating that code was generated by AI.
* Never write default commit messages that give hints of AI-generated code.
* Do not add any AI-specific configuration files (like `.cursorrules` or
  `.copilotignore`) outside of the `.agent/` directory.
