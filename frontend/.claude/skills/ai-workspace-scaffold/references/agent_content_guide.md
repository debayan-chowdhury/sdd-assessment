# Generating `.agent/` content for a given stack

`.agent/` is the control plane: rules that are always-on, and workflows that are
triggered on demand. Unlike `.ai-context/`, every file here gets **real, filled-in
content** — never a skeleton — because these rules must be actionable the moment
the folder exists.

Write all of these fresh for the stack the user named. Don't paste a Node.js
example and swap the word "Node.js" — the categories below are fixed, but the
actual rules (idioms, error-handling pattern, package manager, test framework,
lint tool) must be genuinely correct for that stack. If the user names a stack
this guide has no worked pattern for, use general engineering best practice for
that ecosystem — the structure still applies.

Filenames use the stack slug, lowercase, hyphenated (e.g. `node`, `python`,
`java`, `dotnet`, `react`, `flutter`).

## 1. `.agent/rules/int-standards.<stack-slug>.md`

Five fixed sections, in this order. Each bullet must be concrete and specific
to the stack's idioms — not generic advice that could apply to any language.

1. **Code Style and Structure** — language version/syntax conventions, module
   system, naming, function size/modularity.
2. **Error Handling** — the stack's idiomatic error/exception pattern, logging
   (name a real logging library for that ecosystem, not `console.log`
   equivalents), API error response shape.
3. **Security** — secret management (env vars / stack-appropriate secret store),
   input validation/sanitization, avoiding dynamic code execution.
4. **Performance** — the stack's known bottleneck class (event-loop blocking
   for Node, N+1 queries, GC pressure, etc.) and how to avoid it; DB/query
   optimization.
5. **Guardrails** — always include these three, verbatim, regardless of stack:
   - Never include comments indicating that code was generated by AI.
   - Never write default commit messages that give hints of AI-generated code.
   - Do not add any AI-specific configuration files (like `.cursorrules` or
     `.copilotignore`) outside of the `.agent/` directory.

Worked example (Node.js) for calibration — see the sample this pattern was
extracted from in `references/node_example.md`.

## 2. `.agent/rules/.agentignore`

Purpose: keep build artefacts, secrets, and heavy binaries out of the agent's
context window (token cost + hallucination surface, not housekeeping).

Always include these categories, adapted to the stack's actual tooling:
1. **Heavy dependencies** — the stack's package cache/lock dir (`node_modules/`,
   `venv/`/`.venv/`, `.m2/`/`target/`, `bin/obj/`, `vendor/`, etc.) and lockfiles.
2. **Build artefacts & caches** — the stack's build output dirs (`dist/`,
   `build/`, `out/`, `bin/`, `__pycache__/`, `.next/`, `.gradle/`, etc.) and
   coverage/cache dirs.
3. **Environment variables & secrets** — `.env`, `.env.*`, `*.pem`, `*.key`,
   `credentials.json`, `secrets/` (stack-agnostic, always include).
4. **Logs & local databases** — `logs/`, `*.log`, `*.sqlite`, `*.db`.
5. **Media & static assets** — image/video/font extensions, static asset dirs.
6. **AI audit trail** — always end with `.ai-context/prompt_history.md` to
   prevent the agent recursively reading its own log as context.

## 3. `.agent/workflows/code-review.md`

Fixed structure — "Act as a Senior <Stack> Technical Lead", review under four
headers: Security Vulnerabilities, Performance Bottlenecks, Reliability &
Error Handling, Maintainability — then offer isolated fix snippets for the
most critical issues. Swap in stack-specific risk examples under each header
(e.g. SQL injection/XSS/exposed secrets for a web backend; memory safety for
a systems language; widget rebuild cost for Flutter).

## 4. `.agent/workflows/generate-tests.md`

Fixed structure — name the stack's real default test framework (Jest/Vitest
for Node, pytest for Python, JUnit5 for Java, xUnit for .NET, etc.), require
happy path + failure + edge cases, mocking of external dependencies via that
framework's mocking utilities, clear assertions, and Arrange-Act-Assert
grouping. Output the complete test file so it can be copied directly in.

## 5. `.agent/workflows/generate-plan.md`

New in SDD v1.0 — triggers `plan.md` generation from an approved `spec.md`.
Fixed structure — instruct the agent to:
- Read the linked spec's Intent, API Contract, and Acceptance Criteria.
- Produce a plan following the `.ai-context/plans/_TEMPLATE.plan.md` skeleton
  (Derived From, Architecture Approach, Data Model, Constitution Check,
  Explicitly Deferred, Sequencing).
- Check every constitution.md rule explicitly rather than silently.
- Flag (don't silently resolve) anything the spec left ambiguous.
