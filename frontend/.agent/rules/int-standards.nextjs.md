# INT Next.js Engineering Standards

You are assisting an engineering team at INT. Whenever you write, refactor,
or suggest code in this Next.js (App Router) project, you must strictly
adhere to the following rules:

## 1. Code Style and Structure
* Use the App Router (`src/app/`) conventions exclusively — no `pages/`
  directory. Route segments are folders; use `page.tsx`, `layout.tsx`,
  `loading.tsx`, `error.tsx`, and `route.ts` for their designated purposes only.
* Every component is a Server Component by default. Only add the `"use client"`
  directive at the top of a file when the component genuinely needs
  interactivity (state, effects, browser APIs, event handlers) — never add it
  reflexively to "make something work."
* TypeScript is strict (`strict: true` in `tsconfig.json`) — do not introduce
  `any`; prefer precise types/interfaces and `unknown` with narrowing over
  type assertions.
* Use function components with named exports. Use the `@/*` path alias
  (mapped to `src/*`) for internal imports instead of deep relative paths
  (`../../../`).
* Keep components small and single-purpose. Co-locate a route's components,
  types, and helpers under its `src/app/<route>/` folder unless they are
  shared, in which case they belong under `src/components/` or `src/lib/`.
* Style with Tailwind CSS utility classes; avoid ad-hoc inline `style` props
  or new global CSS unless a utility genuinely cannot express the rule.

## 2. Error Handling
* In Server Components and Route Handlers, wrap operations that can fail
  (fetches, DB/API calls) in `try/catch` and never let an unhandled rejection
  reach the framework as an opaque 500.
* Use route-segment `error.tsx` boundaries for expected UI-level failures, and
  `notFound()` / `not-found.tsx` for missing-resource cases — don't hand-roll
  conditional rendering for these when the framework convention exists.
* Never swallow errors. Log with a structured logger (e.g. `pino`) rather than
  bare `console.log`/`console.error` in anything beyond local scratch debugging.
* Route Handlers (`route.ts`) must return structured JSON error bodies
  (`{ error: string, ... }`) with correct HTTP status codes — never leak stack
  traces or internal error details to the client response.

## 3. Security
* Never hardcode secrets, API keys, or credentials. Read them from
  environment variables via `process.env`, and only expose a variable to the
  browser by explicitly prefixing it `NEXT_PUBLIC_` — never prefix a secret
  that way.
* Validate and sanitize all external input (form submissions, Route Handler
  request bodies, search params) before use; prefer a schema validator (e.g.
  `zod`) at the boundary rather than trusting shapes implicitly.
* Never pass unsanitized data to `dangerouslySetInnerHTML`, and avoid
  `eval()`/`new Function()` or other dynamic code execution.
* Treat Server Actions and Route Handlers as public endpoints: re-validate
  authorization/ownership server-side even if the UI already hides the action.

## 4. Performance
* Prefer Server Components and server-side data fetching over client-side
  `useEffect` fetches — this is the App Router's core performance model.
* Use `next/image` for all images and `next/font` for font loading instead of
  raw `<img>` tags or manual `<link>` font imports.
* Avoid unnecessary `"use client"` boundaries — each one grows the client
  JavaScript bundle shipped to the browser.
* Memoize expensive client-side computations (`useMemo`/`useCallback`) only
  when profiling shows a real cost; don't apply them reflexively.

## 5. Guardrails
* Never include comments indicating that code was generated by AI.
* Never write default commit messages that give hints of AI-generated code.
* Do not add any AI-specific configuration files (like `.cursorrules` or
  `.copilotignore`) outside of the `.agent/` directory.
